Two pipelines, one goal: summaries in the house style

Sales-call transcripts land in Supabase with reference summaries already written by a large model. This project rebuilds that generator from scratch: a first pass with an off-the-shelf BART summarizer to see what "free" gets you, then a Qwen3-8B LoRA fine-tune taught to write like the firm's own CRM briefings — prospect named, specifics kept, Next steps and Outcome signal closed out.

Training pairs 305 completed calls pulled from Supabase
Split 268 / 23 train / validation, after outlier filter
Calls delivered 144 summarized by both models
Speaker leakage 128 → 3 of 144 summaries still say SPEAKER_00

01The architecture

One source, two taps into it, two output directories. The baseline reads cleaned transcript files; the fine-tune reads Supabase directly, because it needs the reference summary as its training target — not just the words.

Phase 1 · the control

What an off-the-shelf model gives you

knkarthick/MEETING_SUMMARY is facebook/bart-large-xsum fine-tuned on meeting and dialogue corpora — a 406M-parameter encoder-decoder with a hard 1024-token input window.

Transcripts blow past that window, so summarize.py splits them into ~850-token chunks on sentence boundaries, summarizes each chunk, joins the results, and re-summarizes until the merge fits in one pass. A map-reduce over the call.

It produces grammatical summaries and has no idea what it is looking at. It writes SPEAKER_00 because that is what the input says, and it never learns the prospect's name.

Phase 2 · the actual goal

Teaching a model the firm's house style

The reference summaries in Supabase were written by a large model and encode a real convention: third person, prospect named, specifics kept, closing with Next steps: and Outcome signal:.

So the 305 calls become supervised pairs — the transcript plus metadata as input, the reference summary as the target — and a LoRA adapter on Qwen3-8B learns the transformation. Training is cheap: rank-16 adapters across all linear layers, 3 epochs, fits on a single 24 GB card.

The input format is the interesting part. Turns are re-labelled before the model ever sees them: prospect turns get the name from attendees[0], the salesperson's turns get the literal word rep. The model is never asked to guess who is who.

04What the numbers actually say

Measured across all 144 delivered calls by comparing output/ and output_v2/ directly.

The clear win 128 of 144 → 3 of 144. Speaker-tag leakage in the baseline is near-total; the fine-tune almost eliminates it. This is the single metric that justifies the whole exercise.
Length Baseline median 210 chars, fine-tuned median 945 chars, reference median 734 chars. The fine-tune landed inside the house-style band rather than at its edge.
Format compliance is partial 112 of 144 summaries contain a Next steps: line, but only 33 of 144 contain Outcome signal:. The narrative shape transferred well; the closing convention did not. Worth knowing before anyone treats the output as CRM-ready.
Style fit, not generalization Of the 144 delivered calls, 122 were in the LoRA's training rows, 15 landed in the held-out validation split, and 7 were dropped by the outlier filter. So the aggregate numbers above are mostly a style-fit measurement — how well the model reproduces a style on calls it saw. Only the 15 held-out calls measure generalization, which is too few to report as a number.
The reference set has its own quality problem The reference summaries run up to 7,208 characters against a 500–1,200 guidance, and several are padded with negation filler — not discussed, not mentioned, no competing vendors. Training on them would teach the model to ramble, so 13 of 305 targets were dropped by a heuristic: longer than 1,800 characters, or four or more negation-filler markers.
Truncation is real but bounded 18 of 305 transcripts exceed the 12,000-character cap and lose their tail, which for a sales call is where next steps and outcome usually live. Median transcript is 2,403 characters, so this affects the long tail only — but it is a silent cut, marked in the prompt as [...transcript truncated...].
The input is deliberately asymmetric The deal stage is fed in; the deal outcome is withheld. Outcome is the answer the model is supposed to infer from the call, so including it would make the task trivial and the evaluation meaningless.
Not under version control This directory is not a git repository, unlike its two sibling projects. 305 training records, 144 output pairs and a 2.4 MB adapter sit here unversioned.

05Where the data came from, and where this went next

This is the middle project of three in C:\Projects, and reading it alone hides the upstream and downstream halves.

Upstream

Everything starts in Supabase, in the calls_for_analysis view — a view, not the calls table, which is a separate and disjoint source. Each row carries the ASR transcript in several shapes, speaker-labelled segments, an attendees list, an entities blob, a speaker mapping, a deal stage label, and the reference summary.

The column is misspelled summmary, with three m's. Every script that touches it carries the typo.

The cleaning step that produced data/cleaned/*.txt — fillers stripped, turns kept — happened outside this repo, in the sibling call-summarizer project's extraction work.

Two filters, two populations

  • 144 calls — completed AND duration_seconds ≥ 240. Answered and at least four minutes long, which excludes voicemail and no-audio calls. This is the deliverable set.
  • 305 calls — completed only, no duration filter. This is the training set: more data, and the outliers do not matter as much when they are going to be filtered.

Downstream

call-summarizer picks this up and adds what is missing here: a frozen eval set, a scorer measuring ROUGE, copy rate, duplicate rate and grounding, and a bootstrap confidence interval. Its own notes state plainly that its first ROUGE win was measured on calls that were all in the training rows — the same caveat recorded in the findings above.

Its README also records where the work was heading: a held-out split, then a smaller Qwen3-4B-Instruct adapter on Runpod. Earlier in the sequence, t5-call-summarizer took the T5 route.

What lives where

  • data/cleaned/ — 144 transcripts, one file per call
  • data/cleaned_index.csv — metadata for those 144
  • output/ — Phase 1 baseline, 144 JSONs + CSV + a zip of the whole set
  • output_v2/ — Phase 2 result, new summary beside the original
  • finetune/dataset_raw.json — 305 raw training records
  • finetune/qwen3-8b-lora/ — the adapter itself, plus a local chat template

A note on reading any of the generated summaries: the reference summaries are a style target, not ground truth. They were written by a large model and do contain errors, so "matches the reference" measures imitation, not accuracy. The LoRA faithfully inherited that property along with everything else.
