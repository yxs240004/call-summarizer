Verifying model downloads One API response carries two different hashes of the same file. Checking the wrong one makes a perfect download look corrupt.

Before you trust a downloaded checkpoint — or spend twenty minutes re-downloading one — you have to know which hash the publisher actually means. This page is the checklist, and the trap that cost this project a full wasted re-download.

The one-line distinction

lfs.oid is the sha256 of the file's bytes. xetHash is Hugging Face's Xet content hash. Both appear in the same API entry, for the same file. Compare against lfs.oid. The CDN's ETag is derived from the Xet path, so it will agree with the wrong one.

01What the trap looks like

GET https://huggingface.co/api/models/<repo>/tree/<rev> returns, per file, an entry like this:

json
{
  "path": "model.safetensors-00001-of-00001.safetensors",
  "size": 4548221488,
  "lfs":  { "oid": "aa33250c...", "size": 4548221488, "pointerSize": 135 },
  "xetHash": "4a33a6bd..."
}

Two hashes, one file, two different hash spaces:

fieldvalue herewhat it is
lfs.oid aa33250c… sha256 of the bytes — this is the one you compare against
xetHash 4a33a6bd… Xet's chunk-level content hash, computed over a different representation

In this project EXPECT_SHA had been copied from xetHash. A fresh, rail-enforced re-download then matched the local file byte for byte on all 543 blocks — 0 differing — and the file's own sha256 came out as aa33250c…, the lfs.oid. Nothing was ever corrupt. The constant was.

Why the ETag did not give it away

The ETag on the resolve URL comes off the Xet path, so it agreed with xetHash and appeared to confirm that the local bytes were the wrong ones. An independent-looking signal that shares a source with your assumption is not a second opinion.

02Four checks, and what each can actually tell you

The trap is not the wrong constant by itself. It is that three other checks all pointed the same way, and not one of them could distinguish corrupt from correct.

checktells youcannot tell you
length equals the published size nothing was truncated silent in-place corruption
ETag / CDN path hash what the CDN believes it is serving which hash is the content hash — here it agreed with the wrong one
zero scan for hole regions no unwritten sparse regions left by a resumed partial a mis-offset append, which is non-zero garbage
N evenly spaced probes vs the CDN the sampled bytes agree damage between the probes
sha256 vs lfs.oid the bytes are the published bytes — nothing. This is the decisive one.

The first four are cheap, and worth running. None of them is a verdict. Only the last line is. When a check cannot distinguish your hypothesis from its opposite, it is not evidence — it is a restatement of your assumption in a different unit.

03The rails: fetching a large file safely

The original downloader set a Range header and trusted the answer. It never checked that the status was 206, never checked that Content-Range began where it asked, and never checked the body arrived complete. A CDN answering a ranged request with a 200 — or from a different offset — would have had its body appended in the wrong place: silent corruption that still leaves the file the right length.

Rules for any resumed or ranged fetch
  1. require status == 206
  2. require Content-Range to start with bytes <offset>-
  3. require the body length to equal the bytes you asked for
  4. retry the block, never the whole file
  5. compare each block against the old file as you write, so one pass yields both a verified file and a damage map
python
if r.status != 206:
    raise RuntimeError(f"status {r.status}, expected 206")
cr = r.headers.get("Content-Range") or ""
if not cr.startswith(f"bytes {start}-"):
    raise RuntimeError(f"Content-Range {cr!r} does not start at {start}")
if len(buf) != want:
    raise RuntimeError(f"short body {len(buf)} != {want}")

Working implementation: finetune/refetch_verified.py. It caught a real ConnectionResetError at 948 MB and retried that block — the older downloader would have appended whatever arrived.

04Validating the shard itself

A hash tells you the bytes match the published bytes. It does not tell you the file is loadable — and after a merge, a conversion, or a hand-assembled directory, you want both. Five checks on a .safetensors file, without loading any weights:

  1. the highest tensor end offset equals the file size, exactly
  2. the sum of tensor byte-lengths equals the index's metadata.total_size
  3. every name in weight_map is present in the header
  4. no tensor's data_offsets fall outside the file
  5. read one tensor at each end with torch
python
import json, os, struct
from safetensors import safe_open

size = os.path.getsize(path)
with open(path, "rb") as f:
    (n,) = struct.unpack("<Q", f.read(8))
    header = json.loads(f.read(n))
header.pop("__metadata__", None)

ends = [8 + n + v["data_offsets"][1] for v in header.values()]
assert max(ends) == size, "a tensor runs past the end of the file"

# "pt", not "numpy": numpy cannot represent bfloat16 and raises
# TypeError: data type 'bfloat16' not understood
with safe_open(path, framework="pt") as f:
    f.get_tensor(next(iter(f.keys())))
What these printed on the 2B shard

632 tensors · header 76,648 bytes · data region 4,548,144,832 bytes · file 4,548,221,488 bytes. Data plus header equals the file size to the byte, and the tensor count matches the index's 632 exactly.
