Lesson 06 · Distillation

The knob you never turned One flag changed how many names the shipped model invents — and the metric family called it a tie.

The last experiment in this project was queued for a housekeeping reason and was nearly skipped. It came back moving the one number the mission actually cares about. This lesson is about a parameter that sat in every deployment and in no experiment, and about the reading discipline that keeps a one-in-three result from being oversold into a win.

01An hour that nearly was not worth spending

Lesson 05 ended with the precision question measured: the shipped 4-bit artifact loses 0.0162 ROUGE-1 to the same weights at 16 bits, and that loss belongs to the quantization, not to the engine and not to the random draw. The step queued behind it was a different question, and a weaker one. Every arm in the project decoded at temperature 0.7, top_p 0.9, repeat_penalty 1.05 — the shipped arm, both controls, all of it. Nobody had asked what those three settings were doing.

The reason it was queued late is written into how the plan was worded. Its stated purpose was determinism: “whether the deployment can be made deterministic instead of seed-dependent.” The grounding question — do the invented names come from the sampling or from the weights — was listed second, and had just got smaller: a scorer bug had inflated the deployed arm's count to 324, and the fix brought it to 37, fewer than the 16-bit arm's 46. A 37-name residual is not a reason to spend an hour. So the run went out for the determinism, and it answered the grounding instead.

The habit worth stealing

Decoding reads as plumbing. It appears in every deployment, it is set once in a config file, and it never becomes a variable — so it never gets measured. That is the shape of a parameter that can move your headline metric without anyone noticing. When you next write down “we serve at temperature 0.7,” ask whether that sentence describes the model or merely the harness. Here it was the harness, and it was controlling a quantity the mission was named after.

02Before you spend the hour, prove the switch is real

There was a specific way this run could have produced a confidently wrong answer, and closing it is worth more than the result. Both GGUFs carry temperature 0.7 / top_p 0.9 / repeat_penalty 1.05 baked into their Modelfiles. A request can pass its own options, and Ollama is supposed to prefer those — but if it did not, the “greedy” run would reproduce the sampled run token for token, and the project would have concluded that decoding changes nothing. A correct number, from a switch that was never thrown.

So before committing the hour, three calls were served with --limit 3 --greedy and diffed against their sampled counterparts. All three differ, and they differ in a direction no trivial echo explains: greedy wrote 152 / 183 / 128 tokens where sampling wrote 91 / 157 / 97. Request options do override the Modelfile, the switch is real, and the hour was worth spending.

The general form

A switch you have never seen change anything is not evidence that nothing changed. Smoke the switch before you trust the run: pick the smallest number of calls that can differ, run them both ways, and diff. This is the same move as lesson 03's “verify the check can fail” and as lesson 05's checks that reported success on a chain that ended in an HTTP 500 — a measurement is only a measurement if it had something to fail for.

03What moved, and what the tie hides

The full run is 144 calls on student-blend — the Q4_K_M artifact that ships, at 1.3 GB against the 16-bit tag's 3.8 GB — with --keep-alive 0 to match the sampled run's conditions. Same weights, same engine, same seed. Decoding is the only variable, which makes this the cleanest comparison in the project.

The grounding numbers are the finding. Ungrounded names fall from 37 on 26 calls to 24 on 16 calls, and ungrounded numbers from 105 to 76, while the summaries stay the same length (108.7 words against 108.0). Whatever the sampling was doing, it was making the model commit to proper nouns and figures that appear nowhere in the transcript.

On quality, the honest reading is narrower than the raw numbers invite. Three ROUGE variants were computed, and one of them moved:

Two of three intervals cross zero, so “greedy is better on ROUGE” is not a claim this run supports. What it supports is weaker and still useful: no variant got worse. The improvement claim has to rest on ROUGE-2 together with the grounding counts — and the grounding counts, unlike the ROUGE figures, carry no paired test at all. They are differences of totals. Saying so is part of the result, not a hedge on it.

Predict before you look

You have just read that greedy invents 13 fewer names across 144 calls. Before reading the next section, write down what you think that means for one call you pick at random. Will that call invent fewer names? How much fewer — and what would it mean if the answer were “usually not”? Commit to a number before you continue.

04A difference of totals is not a difference on your call

Call by call, sampling invents more names on 19 calls and greedy invents more on 8. The other 117 tie. So greedy's 24 names are not a subset of sampling's 37 — they are a partly different set of 24. If you picked a call at random and served it greedily, the most likely single outcome is that nothing changed; the improvement lives in the distribution, not in the card.

That distinction is the one that gets lost when an aggregate becomes a promise. “Greedy invents fewer names” is true of the run and false of any particular call, and the gap between those two readings is where a deployment decision goes wrong. The right question is not “will this call improve” but “do I prefer the run with fewer invented names, given that it will be worse on some calls and better on others.”

What a tie is

The same care applies to the two ROUGE intervals that cross zero. A tie is a statement about significance: the run cannot tell you which direction the difference points. It is never a statement that nothing happened. Read “0.0038, CI [−0.0101, +0.0170], tied” as this experiment cannot resolve a difference this small — not as there is no difference. One of those two tells you to run more calls; the other tells you to stop caring.

05What the flag costs

None of this is free, and the costs are the kind that surface later if they are not written down now.

  • It can run away. One of the 144 calls (call_id 92093631892) hit the 900-token cap and ended mid-sentence — the run's only truncation, where the sampled run had none. Greedy cannot escape a loop it has entered; its characteristic failure is precisely the one sampling mostly avoids. This is the field's own neural text degeneration result showing up as a single row in a score file.
  • Copy rate rises slightly, from 0.0117 to 0.0158 — the direction sequence-level distillation is documented to push, and the one a summarizer is most likely to lose quietly.
  • It is slower. A median 18.5 s per call against 16.0 s — 1.16× the wall time, split 1.07× prefill and 1.09× decode, on the 143 calls neither run slept through. It writes a few more tokens (a median 143 against 132). On a machine whose user is waiting, 16% is a real entry in the ledger.

What the flag buys in exchange is determinism. Re-run it and you get the same summaries; the seed-dependence that made lesson 05's arms awkward to compare stops being a deployment concern. A run whose selling point is determinism, that adds a truncation mode and 16% latency, is a trade rather than a fix — which is the whole reason to measure it instead of adopting it.

One row is not a result

The run's total wall time was 181.6 minutes, against the ~75 minutes its own median predicts. The cause is a single row showing 8,088 s — of which 8,080.5 s is prefill, against a 5.2 s decode. The machine went into Modern Standby at 10:03:36 and woke at 12:18:01: 8,065 s, matching that prefill to within about fifteen seconds. Every latency figure above excludes that row. See learning record 0003 for why an application timer cannot see a suspend, and why reading every outlier before naming a cause is the habit that keeps a run readable.

The lesson generalises past this project: run the control for the weaker reason too. The experiment was scheduled to make a deployment tidier and it ended up answering the question the mission was named after — and it was one flag, not a retraining run. The cheapest control on your list is the one you keep deferring because it looks like configuration rather than science.

Ask me

The obvious next knob is the one this run implicated: the 900-token cap and the repetition penalty are what turned one call into a runaway. Ask me to sweep them and find out whether the truncation is avoidable without giving back the grounding gain — that is a real experiment with a predictable failure mode, which makes it a good one to run together.

Primary source

Holtzman, Buys, Du, Forbes & Choi, “The Curious Case of Neural Text Degeneration” (ICLR 2020). It is why sampling is the default at all: greedy and beam decoding produce repetitive, degenerate text, and the fix is truncating the distribution tail rather than adding randomness. Read it against this run — the paper's prior is “greedy is worse,” and here the ROUGE difference was a tie while the grounding difference was real, which is what it looks like when a prior meets a measurement.
