Lesson 02 · after Lesson 01

Audit the teacher A distillation target is training data, not ground truth. Two of the 154 labels in your teacher pass would have taught the student to repeat itself — and you could only read one of them.

In Lesson 01 you chose sequence-level distillation: the student is trained on the teacher's text, because the two models have different tokenizers and logits cannot be compared. That choice has a consequence worth stating plainly. When the teacher was wrong, the student does not see an error signal — it sees a target. So before the pass becomes a dataset, it gets audited.

01 The shape of the pass

Plot every summary's length and something looks wrong before you even read the text. The distribution is not a heap with a thin tail — it is three bins, a void, and two outliers pinned to the ceiling.

Note

The teacher output records no done_reason. There is no field saying stopped versus cut off — so the audit has to infer it, and the only available evidence is that the count sits exactly on the cap.

02 Two ways a generation fails, only one of which you can read

Both capped rows are in the train split. Both would have become blend targets. They are not the same failure, and the difference is the whole lesson — so here is the actual evidence, taken from the two records.

The first row is the failure you would expect: a real summary that slides into a runaway list of one person's name and role, and never stops. Read it and you see the problem immediately.

The second row is the one worth the lesson. It burned the same 900 tokens. It produced 364 characters — about 70 words, a perfectly ordinary two-sentence summary, the kind you would wave through. So where did 900 tokens go?

Two independent figures say the token count is real and not a recording bug. First, 23.75 s is the unique maximum of the seconds column across all 154 rows, and exactly these two rows hold it. Second, 900 ÷ 23.75 = 37.9 tokens/s for both — and 37.9 sits just above the healthy rows' p90 of 37.1 tokens/s, which is exactly where you expect the fastest per-token rate to land once per-call overhead is amortised over maximum work. A mis-recorded count cannot make a wall clock run long.

The finding

Row 116979700381 emitted 900 tokens and only 364 characters of text. The tokens that consumed the rest produced nothing visible — it looped in a space the stored summary never recorded. When it was regenerated, its visible summary came back byte-identical: 364 characters before, 364 characters after. Nothing about the text was ever wrong; it was silently burning the cap.

That kills the obvious audit. A text scan for repeated phrases catches row one (106 repeats of a 6-gram) and finds nothing in row two, whose top 6-gram occurs exactly once. You cannot audit pseudo-labels by reading them. The cap is not a redundant second signal — for this entire class of failure it is the only signal there is.

03 Why a bad label bites harder here

At inference, a model that loops is an annoyance: you re-run it, or a caller notices. In distillation the relationship inverts. Under sequence-level KD the student's loss is pushed toward reproducing the teacher's token sequence, so a degenerate label is not a slightly-worse target — it is an explicit target that says continue repeating. This is the same asymmetry as any supervised setting: noise in a label is not averaged away, it is learned.

There is a second reason specific to decoding. Holtzman et al. (2019) show that likelihood — excellent as a training objective — behaves badly as a decoding objective, producing text that is "bland and strangely repetitive", and that the decoding strategy alone changes output quality from the very same weights. Beam search takes the highest-likelihood continuation at every step. Once a loop has begun, continuing the loop is the high-likelihood path, because the model's own context has made that phrase the most probable next token. Beam width 4 does not protect against this; measured here, it did not prevent it. Our pass was already beam4, and still 2 of 154 rows degenerated.

What we did

Both rows were regenerated with the same model, same prompt, same beam4, and one changed decoding condition: --repetition-penalty 1.1. They came back at 209 and 78 tokens. The pre-repair file was kept as teacher_output.before_redo.jsonl, and each spliced record gained a provenance field: "replaced": "repetition loop at cap; 900 -> 78 tok, penalty 1.1".

The repaired pass now audits clean — 0 flagged of 154, maximum length 275. But the fix is not free, and you should be able to say the cost out loud: two of the 154 labels now come from a different decoding distribution than the other 152. That is a real, if small, unevenness in the training set, and it is recorded rather than hidden. The trade is deliberate — a degenerate label teaches repetition, while a slightly off-distribution one merely teaches a slightly different summary. Stated as a rule: prefer a slightly uneven target over a confidently wrong one, and always leave a record that you made the choice.

04 Your turn — run the audit

The audit is a script in your repo, not a snippet, because you will run it again on the next project. It checks both symptoms, since they catch different failures: finetune/audit_teacher.py.

# the pass as it came back, before any repair

Exercise

Read the two flagged lines and notice what the second column of numbers does. Row one's worst 6-gram repeats 106 times. Row two's repeats once — that column is silent about it. So before you look at the answer: which single number in that output is carrying the detection for row two?
