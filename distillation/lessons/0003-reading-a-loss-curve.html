Lesson 03 · Distilling the summarizer

Reading a loss curve Both arms' training loss fell. Both arms' validation loss rose. The arm that fell lowest is the one you must not ship.

You now have two trained adapters and a training log. By the end of this lesson you will be able to read that log and say, before running any evaluation, which arm is better and roughly how the worse one is broken — and you will know which number in the log is evidence and which is decoration.

01 What the run actually was

Both arms are the same base, the same adapter shape, the same schedule, the same seed. They differ in one thing: the second half of the training file. This is D6 as it was built.

Everything else is shared and deliberately so — r=16, lora_alpha=32, dropout 0.05, all-linear over twelve module types, 2e-4 cosine with 5 warmup steps, batch 1 with gradient accumulation 8, three epochs, seed 0. The twelve targets are worth one glance, because five of them are not attention: q/k/v/o_proj and the MLP trio, plus in_proj_a, in_proj_b, in_proj_qkv, in_proj_z and out_proj — the state projections of the 18 Gated DeltaNet layers. On a hybrid like Qwen3.5 those carry the recursion, so leaving them frozen would have fine-tuned the model while leaving its memory alone.

02 Two numbers, two different questions

A training loop hands you two numbers and they are not the same kind of thing. Training loss is the objective being minimised right now, over the rows in front of it. It can always be driven down, because the model is allowed to memorise. Validation loss is the same measurement on 12 calls the adapter has never seen. It is the only one of the two that is even trying to answer "will this be any good on call 292?".

The skill is not knowing that. The skill is knowing which of them is allowed to change your mind, and what a difference between two arms means when both arms are reading the same 12 rows.

03 Reading it

Three things follow, and only the third one is the lesson.

First, epoch 1 is clean. Neither arm has overfit yet — the control's gap is even slightly negative. Overfitting is not a property of small datasets; it is a thing that happens over steps, and this run gives you one epoch of "not yet".

Second, the learning rate does not explain the rise. The schedule is cosine from 2e-4 down to 0, so the updates shrink monotonically. Anything driven by step size should be settling, not climbing. Validation loss climbing under a decaying schedule is the model moving toward the 142 calls it was shown and away from the other ones.

Third — the actual lesson — the arm with the better training loss is the worse model. By epoch 3 the control has memorised harder than the blend by any measure (0.270 against 0.606) and is further from useful on unseen calls by a factor of two (gap 2.06 against 1.10). Training loss is not a weaker version of the number you want. On this task it anti-correlates with it, and a run where you only logged the training curve would have told you to prefer the control.

04 Why the difference between arms is readable

Either curve alone is ambiguous. 12 validation records is a small sample, and a single seed gives you no error bars at all — the rise could be noise. What rescues the reading is that both arms are measured on the same 12 rows with the same tokenizer, the same step count and the same schedule, so whatever noise is in those rows is in both curves, and the systematic part left over is the only thing that differs: what the second half of the training file contained.

That is the argument for a control arm at all, and it is also why the control had to be the same size (284 rows) rather than the same content — with only 142 training calls, a reference-only arm that did not repeat itself was not available.

The rival explanation, stated rather than buried

Equal volume is not equal diversity. The control sees 284 rows drawn from 142 distinct calls, so it meets each reference twice per epoch, while the blend meets each reference once and each teacher summary once. The control's faster memorisation is therefore also consistent with "it simply saw less variety", and this design cannot separate that from "teacher supervision regularised it". What the comparison does license is the narrower claim: teacher-plus-reference supervision beat reference supervision alone at matched volume and matched step count. The arm that would settle the rest — reference-only over twice as many distinct calls — needs 284 labelled calls, and this project has 154.

05 What the curve predicted

The evaluation had not been run when that table was read, and the curve made a concrete prediction: the control had memorised the contents of 142 reference summaries without learning much about which facts a summary should contain, so on a new call it should produce confident detail that is not in the transcript. That is checkable, and the next lesson checks it. The headline, measured over all 144 benchmark calls:

The prediction held, in kind and in direction: the control does invent names that are not in the call, and it does so on more calls than the blend. But 443 of those 512 are one call — 116308713889, a repetition loop that emitted Roy and Royalty 443 times over 456 words, with a duplicate rate of 0.97. So the honest magnitude is not 11×: take that call out and the control is 69 names across 44 calls against the blend's 46 across 30, which is about 1.5×.

That correction is the last thing this lesson has to teach, and it is why the two numbers belong side by side. An aggregate you have not decomposed will sell you an 11× effect that is really one broken decode wearing 144 calls as a disguise. The curve predicted the kind of failure precisely; the size of it was a single call, and only the per-call field could tell you which. Lesson 04 does that decomposition properly, on every metric at once.

06 Do it yourself

Exercise · 5 minutes, before you read lesson 04

You have the log and the two adapters. Copy finetune/logs_arms.log somewhere you can edit it, and before opening the evaluation, write down three things:

  1. Which arm you would ship, and the one number from the log you are leaning on.
  2. Which of the six eval columns in student_scores.json you expect to separate the arms most, and roughly by how much.
  3. The prediction the curve makes about how the worse arm fails — in a sentence specific enough to be wrong.

What to compare against. A prediction is only useful if it can fail. The third item is the one that matters: "the control will score worse" is not a prediction, because you already know it. "The control will invent entities it memorised from other calls" is — and it is falsifiable in ungrounded_names, which is a per-call field, so you can also check which calls it fails on rather than only the total.

Check yourself

Both arms' training loss fell. What does the fall show?

What did the control arm not match about the blend?

What did the validation curve predict about the control?

07 Primary source

  • Karpathy — A Recipe for Training Neural Networks (2019). The primary source for §02 and §04. Its first instruction is to become one with the data and set a dumb baseline, and its central habit is exactly the one this lesson teaches: predict what the loss curve will do before you look at it, so that a surprise is information. Read it for the discipline of treating a training run as an experiment you have to have an opinion about.
  • Zhang, Bengio, Hardt, Recht & Vinyals — Understanding Deep Learning Requires Rethinking Generalization (ICLR 2017). The extreme version of §03: models that fit random labels perfectly still train to zero loss, which is why "it converged" and "it will work" are separate claims. Read it when you want to know how far train loss can be from usefulness in principle.
  • Lesson 02 — Audit the teacher. The other half of the training file: which labels the teacher supplied, and the two degenerate ones that had to be regenerated before this run could be trustworthy.
