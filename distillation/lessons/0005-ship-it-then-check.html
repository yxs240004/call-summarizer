Lesson 05 · Distillation

Ship it, then check Five numbers that were reported fields rather than measurements — and the control that finally separates precision from the engine.

Every check in the deployment chain reported success, and the model returned HTTP 500 on its first request. That is not bad luck; it is what a check that cannot fail looks like. This lesson is about the difference between a tool telling you a number and a tool telling you something true — and about the one experiment that turned this project's last open question into a measurement.

01The chain that ended at “created”

Qwen3.5-2B carries a one-layer multi-token-prediction head. The merge step dropped it — correctly, because nothing trained that head toward summarization and 4-bit decoding never touches it — and reported the drop. But the converter computes the block count as num_hidden_layers + mtp_num_hidden_layers, and this checkpoint's config does not name its text model at the top level, so the converter never learned the head was gone. It wrote metadata declaring 25 blocks. The merge had written 24.

Then four tools reported success in a row.

The first real request returned check_tensor_dims: tensor 'blk.24.attn_norm.weight' not found. Neither llama-quantize nor ollama create could have caught it: the first walks the tensors that are in the file and never asks whether the metadata implies more, and the second copies a blob and reads its header. A load failure is invisible from the GGUF side. The fix was to stop declaring the block at all — and the lesson is that the drop was already reported at merge time; reporting it turned out not to be the same as acting on it downstream.

02Five checks that passed for the wrong reason

That was not the first time. Reading the build record end to end, the same shape appears five times: a number or a verdict that is true, produced by something that could not have known whether it was true.

The checkWhat it reportedWhat it actually established
Ollama's chat template the model ran that a Go template parsed — not that the prompt matched the Jinja the student was trained on
GGUF conversion metadata success; 320/320 tensors; 5.37 BPW that the tensors present are quantizable — not that the header describes the same model
verify_merged.py mismatch that bf16 rounds differently from exact arithmetic — at a resolution the format cannot hold
measure_local.py prefill 10,000+ tok/s that Ollama had already seen this exact prompt, so nothing was prefilled at all
verify_quant.py prefix agreement FAIL, 0.0251 against a 0.3215 floor that one early argmax flip rewrote the decode trajectory — not that quality fell

The middle row is the one worth pausing on, because its repair is the model for the rest. The old merge check compared greedy token ids exactly between the adapter and the merged checkpoint. Those two are equal in exact arithmetic and different in bf16, so one position where the top two logits sit within a rounding step flips the token and rewrites the context for every token after it. The test was not wrong about its measurement; it demanded a resolution the arithmetic does not have. The rewrite is teacher-forced and reads its result against a measured floor — the same forward pass twice, which came back bit-identical at exactly 0.0. Against that floor the real effect is small and legible: KL ~2×10−3, same token chosen at 98.5% of positions, and every mismatch sitting at a reference margin of 0.00000, 0.0625, 0.125 or 0.25 — precisely bf16 ULPs at that logit magnitude.

The pattern

A check needs three things: something it could fail for, a floor it can be read against, and a reason to believe the floor is about the quantity you care about. Miss any one and you get a number that is arithmetically correct and answers the wrong question. When a reported field implies something the hardware cannot do — 10,000 tok/s of prefill on a CPU — the field is wrong, not the hardware.

03The number that was missing

All of that checking left the mission's actual question unanswered. Step 5 measured the 16-bit adapter's quality; step 6 measured the quantized file's speed. The artifact that would ship had a measured latency and no measured quality at all. So the deployed model's 144 summaries were scored the same way as everything else — same calls, same references, same scorer, so the number is comparable rather than merely plausible.

Paired, the gap is +0.0114 [+0.0001, +0.0230] and real on all three ROUGE variants. Real by a whisker: the lower bound sits at +0.0001, so this is a difference 144 calls can just resolve, and one more bad call could erase it. That is worth saying plainly rather than rounding up to “significantly worse.”

The interesting part is not the size of the gap but its shape, and the shape is only visible if you look at the distribution instead of the total. The control arm — the deliberately mis-trained arm from Lesson 03 — also had a bad ungrounded-name count, 512 of them. But 443 of those came from a single runaway call, 86% of the arm's whole total. The deployed model's 37 are spread over 26 of 144 calls, almost all of them singletons, with the worst call contributing 4. Same- looking aggregate, opposite kind of failure: one is an outlier to filter, the other is a drift to fix.

That paragraph is where this lesson gets to catch itself, so it stays with its own mistake visible. The first version of the table above said 324 ungrounded names on 139 of 144 calls, and read as a systematic fabrication problem across essentially the whole eval set. It was not a fact about the model. The scorer keeps a registry mapping each variant to the text it actually read, and looks it up with a default. Every Qwen-family arm was registered; the deployed artifact was scored under a new variant name that nobody had added, so it fell through to the default — raw ASR with anonymised SPEAKER_00 labels, in which the call participants' names never appear, so every summary that names the person on the call reads as invented. Against the corpus the model actually read, the figure is 37. ROUGE never touched that corpus, which is why the quality column was right the whole time and the fabrication column was wrong by a factor of nine.

Two things are worth taking from it. A fix that consists of adding the new name to the list does not survive the next name — the earlier variant had been registered for exactly this reason, and the bug came straight back under a different label. And the deployed model turns out to invent fewer names than anything else measured: 37 against the 16-bit student's 46, the tuned 4B's 47, the untuned 8B's 107 and the teacher's 109. The registry now stops instead of guessing, so the next new variant fails loudly rather than producing a plausible number.

Reading the losing calls shows what the drift actually is, and it is not invention. The deployed arm writes 33 words shorter on 110 of 144 calls, and on its three worst it produced 80, 70 and 130 words where the 16-bit arm produced 151, 158 and 81 against references of 181, 171 and 113. ROUGE rewards carrying the call's content, so a summary that drops a third of it loses heavily while inventing nothing. Where it does add names, they are mostly glosses of acronyms it should have left alone — RCFO (Rico fee…, BP303…) where the reference reads Arco fee, Arco Johnson. And some garbling is shared with the 16-bit arm, so it is inherited from the 2B rather than introduced by 4 bits.

Structurally, nothing about this output looks broken, which is the point. All 144 calls stop of their own accord rather than hitting the 900-token cap; none is empty, none ends mid-sentence, none opens with “Here is a summary,” and the duplicate rate is 0.001. A pipeline that tested for empties, truncations and preamble — the usual smoke tests — would report this model as clean. Every bit of the damage is in content that is present, well-formed, and quietly incomplete.

04Change one thing at a time

Here is the trap, and this project walked into it. The comparison above moved more than one thing at once — and which things is a question you answer by reading the generator, not by recalling what you think you ran. This lesson is about figures that answer a question they were not designed to answer. The honest version of this paragraph is that an earlier draft of it answered one.

That draft said the two arms differed in decoding: the served run samples at temperature 0.7, it said, while the 16-bit arm decoded greedily. It does not. student_generate.py:135 reads do_sample=True, temperature=0.7, top_p=0.9, repetition_penalty=1.05 — the same three numbers the served run sends. Sampling was never the confound, and “greedy versus sampled” was a remembered property of a different experiment, written into a field that then travelled into three other documents before anyone re-opened the file.

What actually differs is engine, draw, and precision. The 16-bit arm ran inside transformers, from an unseeded draw; the served run is llama.cpp through Ollama at seed 42; and one of the two is quantized. Three things, one number, and no way to say which of them the 0.0114 belongs to.

The fix is cheap, and it is the same move the last section made: change one thing. Serving the 16-bit GGUF through the same engine at the same sampling and seed makes the two Modelfiles differ in exactly one line — the source file — and makes the two runs share their random draw, so what separates them is precision rather than luck. It is a tighter control than the one this section originally proposed, and tighter for an unflattering reason: the variable it was designed to remove was never there.

Predict before you look

If you were writing this section for your own project, the first move is to re-open the generator and list the settings each arm actually used, rather than trusting the note you wrote when you launched it. Do that now, before the next paragraph gives you this project's answer, and write down every field where the two arms disagree. Then predict where the f16 control lands: near 0.428, or near 0.440. A prediction you committed to turns a result into information; the same result read afterwards is just a story.

It landed at 0.4447. Above both candidates, which is its own small lesson in why you run the thing. Here is the arithmetic, over the same 144 calls in the same input order:

The first row is the surprise, and it is the reason to run a control rather than reason about one. Through llama.cpp at a fixed seed the same 16-bit weights score 0.4447 against 0.4399 inside transformers — a difference of −0.0048 with an interval straddling zero, and in the opposite direction to the guess that the engine was the problem. Engine and draw cost nothing measurable; if anything llama.cpp comes out marginally ahead, while writing 16 words fewer (125.0 against 141.2).

That leaves the second row, and it is the one that matters. The loss is the quantization. +0.0162 with a lower bound of +0.0057 is comfortably clear of zero, and it is the term the mission actually spends money on: it is what you pay, in quality, for a file a third the size. The third row is the proof that the split is exhaustive rather than merely plausible — −0.0048 and +0.0162 sum to +0.0114, the bundled figure to the digit.

The uncomfortable half is what that arithmetic does to the bundled figure. Because the engine term happens to pull the other way, inside its own noise, the three-way comparison was diluting the effect it was reporting: it published “real by a whisker,” a lower bound of +0.0001, for a quantity whose true lower bound is +0.0057. Nothing in it was mismeasured. A number answering a question it was never designed to answer is exactly what the control went and unpacked.

Caveat to carry

Seed 42 fixes the draw, not the output. Different logits mean the token streams still diverge, so the seed removes the draw as a nuisance variable rather than making the two arms comparable token for token. It narrows the question; it does not delete it.

05What this buys the mission

The mission asked for a model that runs locally without heavy resource use and writes summaries “almost as good as the teacher.” Both halves now have numbers rather than hopes. The shipped artifact scores 0.4285 ROUGE-1 against its teacher's 0.4784 — about 89% — and sits at ~96% of its own unquantized self as served through the same engine (0.4447), at a median 16 seconds per call on CPU, which is about 78 minutes for the 291-call set run one at a time. “Almost as good” holds. The honest form of it is: almost as good, with a measured, small and statistically real gap of 0.0162, whose cause is named and whose control has run.

The resource half has a measured shape too, and it is not the one the file sizes suggest. The two GGUFs weigh 1.27 GB (Q4_K_M) and 3.78 GB (f16) — a factor of 2.96 — but on the 142 calls neither run slept through, f16 served 1.85× the wall time per call (a median 29.0 s against 15.7 s; over all 144 the shipped arm's median is 16.0 s). The split is the informative part: 1.54× in prefill and 2.51× in decode. Prefill sits far below f16's own 2.96× size ratio and decode sits just under it, which is what a compute-bound prefill beside a bandwidth-bound decode should look like on this class of CPU. It is cheaper than its own size, and that is the reason.

There was a second reason, and this lesson has to take it back. One f16 call spent 1,950 seconds decoding 211 tokens — an apparent 250× collapse that made the larger model look fragile rather than merely slow. The explanation written down was memory pressure: Ollama memory-maps the GGUF, a 3.78 GB mapping is a trimmable target the moment the system wants memory back, and the 1.27 GB artifact keeps its pages. It was a good story. It was wrong. Windows keeps a record of its own power transitions, and reading it shows a 1,936-second Modern Standby suspend spanning that decode, entered after the call had already started — plus a second outlier in the same run that ends on the second of a logged wake. The laptop slept. No page was evicted, and the smaller file was never the sturdier one; it is only faster.

The honest version of the argument is the dull one: 1.85× the latency and 2.96× the disk, for +0.0162 ROUGE-1. That is still enough to quantize when a person is waiting on every call — a 3.8% relative gain in quality does not buy back nearly doubling every wait — but it is a trade, not a free lunch and not a durability. And the clause that used to stand here, “for no gain in quality,” is the same shape as everything else on this page: a figure answering a question it was never designed to answer. One event-log query settled the paging story; one control run settled this one.

That is the difference this lesson is about. A number you can defend is not one that sounds precise; it is one where you know what it would have taken for it to be wrong, and you went and looked.

06Primary source

  • Sculley, Holt, Golovin, Davydov, Phillips, Ebner, Chaudhary, Young, Crespo & Dennison — Hidden Technical Debt in Machine Learning Systems (NIPS 2015, pp. 2494–2502). The paper that names both halves of this lesson. Its configuration debt section is the MTP failure in one sentence. And §2’s CACE principle — Changing Anything Changes Everything — says that CACE “applies not only to input signals, but also to hyper-parameters, learning settings, sampling methods, convergence thresholds, data selection, and essentially every other possible tweak.” That list is why the f16 control exists: precision, engine and draw all changed at once, and the paper tells you to expect exactly that entanglement. It also predicts the harder half of this lesson — that the confound you name is another reported field, and has to be read off the code that ran.
